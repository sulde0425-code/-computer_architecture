0.5 · 切换章节：以 EXP6（第 4 章 · 访存指令）为例

本指南正文以 EXP4 为例，但流程对任意章节完全通用。下面给出切到 EXP6 的完整参数与命令。

EXP6 = 教材第 4 章「访存指令的添加」，对应镜像 for_test_obj/ex6_obj， 验证指令 ld.b / ld.h / ld.w / ld.bu / ld.hu / st.b / st.h / st.w， 共 39 个功能测试点（编号 01→39）。
判别指纹：inst_ram.coe md5 = a76338349250a0465346deb004e4c1db， 共 123101 字；与 ex5 的第 8224 个字即不同（ex5=5080d800，ex6=50810800）。

0.5.1 一键切换（推荐，带校验与回滚备份）

# 在 Main_project_1.1/ 下执行
bash .workbuddy/sim/switch_exp.sh 6

它会做三件事：

  1. 把旧镜像 + 旧 golden_trace.txt 备份到 mycpu_env/.bak_<时间戳>/；
  2. 把 ex6_obj 的 .coe/.mif 同步到 三个位置（见下一节）；
  3. 逐项 cmp 校验，任何一处不一致就报错退出。
必须同步的三个位置（漏一处就会"仿真对、上板错"）：
文件谁读它

xilinx_ip/inst_ram/inst_ram.mifgenerate_target 生成 IP 产物时读这里

0.5.2 出 bit —— 关键在于必须重跑 IP 的 OOC 综合

★ 这是本项目最大的坑，也是之前「每章都 69 分」的根因。

inst_ram 是 blk_mem_gen IP，采用 OOC（out-of-context）综合。 主综合 synth_1 只引用它的 stub，真正把程序数据烧进 BRAM 的是 loongson.runs/inst_ram_synth_1/inst_ram.dcp。

换 Coe_File 后：
  • generate_target 只更新 IP 目录下的 .mif 和仿真模型，不会重跑该 dcp；
  • 只做 reset_run synth_1 也不行 —— Vivado 会认为 IP "checkpoint is already up-to-date" 而跳过，bit 里仍是上一套程序。

必须显式重跑 OOC run： 
reset_target all [get_ips inst_ram]
generate_target all [get_ips inst_ram]
reset_run  inst_ram_synth_1      # ← 缺了这步，程序就换不掉
launch_runs inst_ram_synth_1 -jobs 16
wait_on_run inst_ram_synth_1

上面全部步骤已封装进脚本，一条命令即可：

D:/Xilinx/Vivado/2023.2/bin/vivado.bat -mode batch -source .workbuddy/sim/rebuild_bit_expN.tcl -tclargs 6

脚本会自动：disable 原 soc_lite_top.xdc（PPT 教程步骤 5）→ 重跑 IP OOC → 主综合 → 实现 → 出 bit → 导出时序/资源报告 → 按实验号归档为 .workbuddy/sim/exp6/looongson_remote_top_EXP6.bit 并在工程根目录放一份同名文件。全程约 13 分钟。

0.5.3 出完 bit 怎么确认装的是不是 ex6

看 OOC 产物的时间戳，必须比你换镜像的时间更晚：

ls -l --time-style=+"%m-%d %H:%M" \
  cdp_ede_local-master/mycpu_env/soc_verify/soc_bram/run_vivado/project/loongson.runs/inst_ram_synth_1/inst_ram.dcp

更严格的做法是从 dcp 里把 BRAM 的 INIT_00 抽出来，反推前几个字节与 ex6_obj/inst_ram.coe 比对 （ex6 的头 8 个字与 ex4/ex5 相同，所以用前 8 字节判别不出来，要取 word[8224]=50810800 附近的区域）。

1 · 必须先搞懂的一件事：仿真和综合，读的镜像文件不是同一个

这是整个流程里最容易踩空的地方，也是很多人"明明改了程序却测的还是旧程序"的根因。

场合谁来提供存储器从哪里取程序/数据换镜像要动什么
行为仿真
Run Behavioral Simulation		 testbench/sync_ram.v 里用 $readmemb 写的行为级 RAM。
它定义了同名的 inst_ram/data_ram，编译时覆盖掉 Xilinx IP 的版本（日志里会有 VRFC 10-3609 overwriting previous definition 的 WARNING，这是正常且预期的）。		 func/obj/inst_ram.mif
func/obj/data_ram.mif		 只复制两个 .mif
综合 / 实现 / 出 bit
Run Synthesis → Bitstream		 Xilinx IP inst_ram / data_ram func/obj/inst_ram.coe
（写在 inst_ram.xci 的 Coe_File 里，Load_Init_File=true）
data_ram 的 Load_Init_File=false，即综合出来无初值，靠程序自己写		 复制 .coe，并 Reset + Generate Output Products
两条铁律：
① 只跑仿真 → 复制 .mif 就够了，不需要动 IP；
② 要出 bit 上板/上传 → 必须复制 .coe 并重新生成 IP 输出产物（IP 的初始化数据在生成时就固化了，只换文件不重生成=没换）。

1.1 先确认当前装的是哪一套

光看文件名看不出来。用校验值比对，几秒钟就能确定：

# 在工程根目录 Main_project_1.1/ 下执行
for d in for_test_obj/ex*_obj; do printf "%-24s " "$d"; md5sum "$d/inst_ram.coe" | cut -d' ' -f1; done
echo -n "当前 func/obj 装的是:  "; md5sum cdp_ede_local-master/mycpu_env/func/obj/inst_ram.coe | cut -d' ' -f1

EXP4 的 inst_ram.coe 校验值应为 ae68ae9f8608137892c477ef6dd2c5f1。

2 · 流程 A：行为仿真（判断"功能对不对"）

步骤 1 装入 EXP4 的镜像（仿真只需两个 .mif） 
cp for_test_obj/ex4_obj/inst_ram.mif  cdp_ede_local-master/mycpu_env/func/obj/inst_ram.mif
cp for_test_obj/ex4_obj/data_ram.mif  cdp_ede_local-master/mycpu_env/func/obj/data_ram.mif
路径必须就是 mycpu_env/func/obj/：sync_ram.v 里写死了相对路径 ../../../../../../../../func/obj/inst_ram.mif，换别处它读不到。
步骤 2 重新生成 golden_trace.txt（漏了这步仿真必然满屏报错）

测试平台把每条指令的 PC / 写哪个寄存器 / 写了什么值 与"黄金模型"逐条比对，所以黄金 trace 必须和当前镜像同源。打开 mycpu_env/gettrace/gettrace.xpr，直接 Run Simulation → Run Behavioral Simulation，跑完自动写出 mycpu_env/gettrace/golden_trace.txt。

这个黄金模型是纯 Verilog，不需要交叉编译工具链，只要能跑 xsim 就行。

成功标志：日志里出现 gettrace end! 和 ----Succeed in generating trace file!， 并且 golden_trace.txt 被刷新。EXP4 应为 62377 行。

步骤 3 跑 CPU 的行为仿真
  1. 打开 cdp_ede_local-master/mycpu_env/soc_verify/soc_bram/run_vivado/project/loongson.xpr
  2. Flow Navigator → Simulation → Run Simulation → Run Behavioral Simulation
  3. 看底部 Tcl Console 的输出

Tcl Console 等价命令（不想点鼠标就贴这个）：

set_property top tb_top [get_filesets sim_1]
launch_simulation
run 5 ms        # 不要用 run all，理由见下
close_sim
为什么是 run 5 ms 而不是 run all：测试平台里有个 while(num_monitor) 循环，只要测试点计数还在变就一直打印 Test is running…。 CPU 一旦跑飞，这个循环永不退出，run all 会一直挂着不返回。给个时间上限就能安全收尾。 （EXP4 正常情况在 806 µs 左右就自己 $finish 了，5 ms 绰绰有余。）
★★ 最常见的"仿真没反应"陷阱：launch_simulation 只跑 1000 ns ★★

Vivado 点 Run Behavioral Simulation 时，会自动生成一个 tclbatch 文件，它的最后一行是 run 1000ns（可以打开 loongson.sim/sim_1/behav/xsim/tb_top.tcl 自己看）。也就是说 launch_simulation 跑完就返回时，仿真只推进了 1000 ns，日志末尾会写：

INFO: [USF-XSim-97] XSim simulation ran for 1000ns

而 mycpu_tb.v 里复位要在 2000 ns 才释放：

resetn = 1'b0;
#2000;
resetn = 1'b1;   // ← 2000ns 之前 CPU 根本没开始工作

所以 1000 ns 时连 Test begin! 都不会打印，看起来像"什么都没发生"。这不是错，是还没跑完。 EXP4 要跑到约 806 µs 才会 $finish。

正确做法 —— 在仿真已启动的状态下，往底部 Tcl Console 再补一条命令：

run 5 ms        # 或点菜单 Run → Run for 5 ms
close_sim       # 看完结果再关

完整日志落在 loongson.sim/sim_1/behav/xsim/simulate.log，可以直接搜 PASS 和 Error。

一键脚本：上面步骤 1+2+3 已经串成 .workbuddy/sim/verify_exp4.tcl（里面已经用了 run 5 ms）。在工程根目录执行： 
D:/Xilinx/Vivado/2023.2/bin/vivado.bat -mode batch -source .workbuddy/sim/verify_exp4.tcl
它会自动换镜像 → 重生成 golden_trace → 跑 EXP4 仿真 → 打印结果。实测约 1 分半跑完。

4 · 怎么判断实验成功（核心）

4.1 仿真：四个信号，全部满足才算通过

日志里应该看到含义
① Test begin! 测试开始
② ----[   12105 ns] Number 8'd01 Functional Test Point PASS!!!
----[   36515 ns] Number 8'd02 Functional Test Point PASS!!!
…
----[ 805635 ns] Number 8'd29 Functional Test Point PASS!!!		 每点亮一个"功能测试点"打印一行。编号必须从 01 开始严格连续、无跳号无重复——跳号就说明某条指令算错了
③ ==============================================================
Test end!
----PASS!!!		 唯一的"总判定"。全程零错误，结尾必然是 ----PASS!!!
④ 全程搜不到 Error 字样 指令级比对错误数 = 0，测试点错误数 = 0
EXP4 的成功判据（本次实测值，可直接对照）：
功能测试点数29 个，编号 01→29 连续
指令级比对错误0
最后一个功能测试点的时间805635 ns
结束时间806125 ns（程序 $finish）
结尾----PASS!!!

日志里还会穿插两类"看起来像错误、其实正常"的行，不用管：

  • Test is running, debug_wb_pc = 0x… —— 每 10 µs 一句进度心跳；
  • 程序自己往 UART 写的字符（$write("%c", uart_data)）—— 测试程序自己的打印，用于人工核对。

4.2 失败信号对照表

日志里的字样含义先查什么
[t] Error!!!
reference: PC = 0x…, wb_rf_wnum = 0x…, wb_rf_wdata = 0x…
mycpu   : PC = 0x…, wb_rf_wnum = 0x…, wb_rf_wdata = 0x…		 最致命。某条指令的 PC / 目标寄存器 / 写回值和黄金模型不一致。打印后立刻 $finish，仿真到此中断，后面的测试点一个都不会有。 ① 镜像和 golden_trace.txt 是不是同一套（最常见）
② 出错的 PC 是不是 EXP4 新增的 9 条指令之一
③ 该指令的译码 / 控制信号
Error(N)!!! Occurred in number 8'dNN Functional Test Point! 测试点编号跳号 → 某条指令算错，程序没能点亮该点 编号 NN 对应 ex4_obj/test.s 里第 NN 个测试段，去看那几行汇编
Error(N)!!! Unknown, Functional Test Point numbers are unequal! 测试点高低位编号不同步 一般说明 CPU 跳飞了
Fail!!!Total N errors! 程序跑到终点，但有 N 个错 看上面的 Error 明细定位
一直刷 Test is running, debug_wb_pc = 0x…，PC 不变或乱跳，且长时间不结束 CPU 卡死或跑飞 PC 值能反推卡在哪条指令附近
VRFC 10-2096 empty statement in sequential block mycpu_tb.v 里有空语句，xvlog 直接拒绝编译 本工程已修复（改为 if(uart_data!=8'hff)）。若又出现，说明文件被还原了
VRFC 10-3609 overwriting previous definition of module 'inst_ram' 正常的 WARNING，不是错误 这正是 sync_ram.v 的行为级 RAM 覆盖 IP 版本，仿真走的就是行为级

4.3 上板 / 上传平台的判据

  • 先看时序：Timing Summary 里 cpu_clk_clk_pll 一行必须 WNS ≥ 0 且 TNS = 0（保持时间 WHS 也 ≥ 0）。 WNS < 0 的 bit 绝对不要上板——它的错是偶发的（跟温度、电压、布局有关），非常难查，很容易"仿真全过、上板全错"。
  • 板上表现：串口打印测试程序输出；confreg 的 num_monitor 计数递增；程序跑完停在 0x1c000100。
  • 平台评测：上传 bit → 远程 FPGA 自动评测，含功能测试与性能测试两部分。

5 · EXP4 要验哪些指令

教材 3.1 节原文："添加算术逻辑运算类指令 slti、sltui、andi、ori、xori、sll、srl、sra、pcaddu12i。运行对应的 func，要求成功通过仿真和上板验证。"

镜像要添加的指令测试点数
ex4_obj slti、sltui、andi、ori、xori、sll(.w)、srl(.w)、sra(.w)、pcaddu12i 29
ex5_obj blt、bge、bltu、bgeu 33 （同属第 3 章）
三个已知的编码坑（本 CPU 已在第 3 章修正）：
  • SLTI = 0x8、SLTUI = 0x9（op[31:26] 属 2RI12 类），极易和 ADDI.W = 0xA 混淆；
  • SLTUI 的立即数仍然做符号扩展，不是零扩展；
  • 写回使能 gr_we 必须"正向译码"而非"反向屏蔽"——否则未译码的指令会被当成合法指令执行并写坏寄存器堆（症状就是"加了几条指令后，别的章节开始莫名失败"）。

6 · 检查清单（照着打勾）

  1. 镜像换成 ex4_obj 了吗？func/obj/inst_ram.coe / .mif 校验值对不对？
  2. 只跑仿真 → .mif 复制到位即
    要出 bit → .coe 复制到位 并且 Reset + Generate 了 inst_ram IP
  3. gettrace/golden_trace.txt 重新生成了吗？（EXP4 = 62377 行）
  4. 仿真结尾是 ----PASS!!! 吗？29 个测试点是否 01→29 连续？
  5. 实现后 cpu_clk_clk_pll 的 WNS ≥ 0 吗？
  6. 准备上传的 bit 是最后一次实现出来的那个吗？（改过 RTL 就必须重新生成）

7 · Vivado 日志里那些 WARNING：哪些要管，哪些不用管

综合 / 仿真跑完，Tcl Console 里会刷一堆 INFO 和 WARNING。本工程正常跑通时一条 ERROR 都不该有，下面这些是常态，看到不用慌：

日志原文级别要不要管
[USF-XSim-97] XSim simulation ran for 1000ns 注意 要管。说明仿真只跑了 1000 ns 就返回了，需再补 run 5 ms。见上文红框
[VRFC 10-3609] overwriting previous definition of module 'inst_ram' / 'data_ram' 正常 不要管，且是好事。这正是 testbench/sync_ram.v 的行为级 RAM 把 IP 版本覆盖掉了——证明仿真读的是 func/obj/*.mif
[VRFC 10-3129] assignment to input 'dina' 正常 不要管。官方自带 sync_ram.v 的写法瑕疵，行为正确
[Vivado 12-13340] Unable to auto find GCC executables from simulator install path! (path not set) 正常 不要管。本设计不使用 DPI-C（dpic.v 已删除），gcc 用不到
[Simtcl 6-197] One or more HDL objects could not be logged because of object type or size limitations 正常 不要管。256 KB 的存储器数组太大，波形记录器跳过它而已
[filemgmt 56-3] Default IP Output Path : Could not find the directory '…/loongson.gen/sources_1' 正常 不要管。IP 是 OOC 方式管理的，不走 loongson.gen
[Vivado 12-4149] The synthesis checkpoint for IP '…/data_ram.xci' is already up-to-date 正常 不要管。复用已有的 IP 综合检查点
[ProjectBase 1-489] The host OS only allows 260 characters in a normal path. The project is stored in a path with more than 80 characters… 留意 不是错误，但建议留意。本工程路径长达 117 字符（D:/Courses/…/run_vivado/project），再叠加 sync_ram.v 里 8 级上跳的相对路径，接近 Windows 260 字符上限。目前工作正常，若哪天出现"找不到文件"，用 subst 映射短盘符即可：
subst X: "D:\Courses\Computer_organization_design\Main_project_1.1"
[USF-XSim-43] Exported '…/xsim/inst_ram.mif' 正常 不要管。但请注意：仿真实际读的是 func/obj/inst_ram.mif，不是这个导出副本
还有一条容易漏的：这份日志里从头到尾没有出现过 inst_ram 的 IP 重新生成。 如果你是要出 bit（而不是只跑仿真），改了 func/obj/inst_ram.coe 之后必须补上： 
reset_target all [get_ips inst_ram]
generate_target all [get_ips inst_ram]
否则 bit 里固化的仍然是上一套程序 —— 仿真对、上板错，就是这么来的。
