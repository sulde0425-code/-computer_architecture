0 · 学前预备：把流水线想成一条工厂流水线

先给你三个锚点，后面所有内容都挂在这三个锚点上。

锚点一：流水线不是"让一条指令跑得更快"，而是"让很多条指令同时跑"。
一条指令从头到尾要花的时间（延迟 latency）其实变长了一点点（多了级间寄存器的建立时间）， 但吞吐率 throughput 提高了——理想情况下每个时钟周期都能完成一条指令。 汇报时如果老师问"流水线快在哪"，答吞吐率，别答延迟。
锚点二：每一级之间必须有一排寄存器（流水线缓存），否则各级会互相污染。
组合逻辑是"立刻生效"的。如果 IF 算出的 PC 直接连到取指、ID 又马上译码，那么新 PC 会一路冲到底， 把前一条指令的中间结果全部冲掉。加一排寄存器后，每一级在某一拍看到的，永远是"上一拍上级送来的那一条指令"。
锚点三：五级流水线里，一切的复杂性都来自两个字——"相关"。
后一条指令要用前一条指令的结果。第 1 章故意不处理这个问题（所以第 1 章的 CPU 是"错"的， 只是错的指令恰好没被测到）；第 2 章就是来解决它的：能前递就前递，不能前递就阻塞。

0.1 五级分别是干什么的

级英文名这一级负责什么本工程对应文件
取指IF 算好下一条指令的地址，送到指令 RAM，把取回来的指令字存进级间寄存器IF_stage.v
译码ID 拆指令字段 → 认出这是哪条指令 → 读寄存器堆 → 生成一整套控制信号 → 分支判断ID_stage.v
执行EXE ALU 运算 / 乘除；算访存地址；给出数据 RAM 的控制信号EXE_stage.v + alu.v
访存MEM 读数据 RAM；按字节/半字做选取与符号扩展；决定最终写回值MEM_stage.v
写回WB 把结果写回寄存器堆；输出 trace 调试信号WB_stage.v + RegFiles.v

记忆口诀：取（Fetch）→ 译（Decode）→ 算（Execute）→ 存（Memory）→ 写（Writeback）。 注意 LA32R 是 LoongArch，没有延迟槽（MIPS 有），所以分支后面那条指令本来就不该执行——后面会看到我们怎么"取消"它。

1.2 级间为什么必须放寄存器：一个反例

假设没有级间寄存器，第 N 拍 IF 把 PC 从 0x1000 改成 0x1004。 这个新值立刻传到指令 RAM，RAM 的输出立刻变成 0x1004 处的指令， ID 又立刻译这条新指令……结果是：0x1000 那条指令在第 N 拍凭空消失了， 它本该在 ID 级做的事全被冲掉。

加了寄存器以后，第 N 拍结束的时钟沿上，0x1000 的"指令+PC"被锁进 IF/ID 之间的寄存器； 第 N+1 拍 ID 级看到的永远是这一份快照，即使这时 IF 已经在取 0x1004 了。这就是"流水线缓存"。

关键理解：级间寄存器里装的不只是数据，还必须装一个 valid 位—— "这个位置里现在到底有没有一条有效指令"。没有它，复位后流水线上全是垃圾数据，CPU 会拿着随机值乱跑。

2 · 握手规范：valid / allowin / ready_go

2.1 三个信号各自由谁产生、送给谁

信号方向含义（一句人话）
valid前 → 后"我这一级现在确实有一条有效指令，可以往下送"
ready_go本级内部"我这一级自己干完活了吗"（算完了 / 等的数据到了）
allowin后 → 前"我下一拍腾得出来，你可以把指令送过来"

把这三个信号想成两个管理员在对话：

  • 前级举手说：我有货（valid）且我这边处理完了（ready_go）；
  • 后级点头说：我这边有空位（allowin）；
  • 两个条件同时成立，这一拍货物才真正往下搬一格。

2.2 三条公式（背下来，老师最爱问）

// ① 本级"能接收新指令"的条件：要么我本来就是空的，要么我能出货且后级收得下
allowin      = !valid || (ready_go && next_allowin);

// ② 本级"对后级有效"的条件：我确有指令，且我自己已经干完活
to_next_valid = valid && ready_go;

// ③ 数据真正写入级间寄存器的条件：前级给了我有效数据，且我收得下
if (to_prev_valid && allowin)  bus_r <= bus;
为什么 allowin 里要有 !valid 这一项？
因为本级是空的时，不需要等自己"干完活"就可以接收——空级没有活要干。 少了这一项会出现死锁：本级空 → ready_go 可能为 0 → allowin 为 0 → 永远接收不了新指令。

2.3 本工程里的真实实现（逐行对照）

IF 级 第 1 章

assign to_fs_valid      = ~reset;          // 复位结束就永远有指令要取（源头）
assign fs_ready_go      = 1'b1;            // IF 级不需要等任何东西（第 1 章）
assign fs_allowin       = !fs_valid || fs_ready_go && ds_allowin;
assign fs_to_ds_valid   = fs_valid && fs_ready_go && ~br_taken;  // ← 多一项，见 §2.5

always @(posedge clk)
    if (reset)              fs_valid <= 1'b0;
    else if (fs_allowin)   fs_valid <= to_fs_valid;   // 接收来自 pre-IF 的 valid

ID 级 第 1 章 第 2 章改造

// 第 1 章：ready_go 恒 1；第 2 章：出现 RAW 且无法前递时必须拉低
assign ds_ready_go    = ~load_stall & ~div_stall & ~mul_stall & ~branch_load_stall;
assign ds_allowin     = !ds_valid || ds_ready_go && es_allowin;
assign ds_to_es_valid = ds_valid && ds_ready_go;

EXE 级 第 1 章 第 5 章改造

assign es_ready_go    = !es_div_inst || es_div_ready;  // 除法要多拍（第 5 章）
assign es_allowin     = !es_valid || (es_ready_go && ms_allowin);
assign es_to_ms_valid = es_valid && es_ready_go;

MEM / WB 级 第 1 章

// MEM：本章的 RAM 一拍就返回，永远 ready
assign ms_ready_go    = 1'b1;
assign ms_allowin     = !ms_valid || (ms_ready_go && ws_allowin);

// WB：最后一级，没有下游，因此 allowin 里没有 next_allowin 这一项
assign ws_ready_go    = 1'b1;
assign ws_allowin     = !ws_valid || ws_ready_go;
对比一下 WB 和前面几级：WB 的 allowin = !ws_valid || ws_ready_go， 没有 && next_allowin——因为它后面没有级了，外面永远收得下（写寄存器堆是瞬间完成的）。 这也解释了为什么"流水线最末级不会成为阻塞源"。

2.4 阻塞是怎么一级一级往前传的

假设 EXE 级正在做除法，es_ready_go = 0：

  1. es_allowin = !es_valid || (0 && ...) = 0（只要 EXE 里有指令）→ EXE 收不下；
  2. ds_allowin = !ds_valid || (ds_ready_go && es_allowin=0) = 0 → ID 也收不下；
  3. fs_allowin = !fs_valid || (fs_ready_go && ds_allowin=0) = 0 → IF 也停住；
  4. 最终 inst_sram_en = to_fs_valid && fs_allowin = 0 → 连取指都停了。
这就是"后面堵了，前面必须立刻一起堵"。 否则前面还在往里塞新指令，后面又出不去，指令就丢了。 整个链条靠的就是 allowin 一级一级往前传——这也是为什么指导书说"每级都要有个管理人员"。

2.5 控制相关：分支时怎么"取消"已取进来的指令

分支在 ID 级 才判断出来（要看寄存器的值）。但这时 IF 级里那条顺序取进来的下一条指令已经在了。 LA32R 无延迟槽，所以它不该被执行。办法极简——把它的 valid 抹掉：

assign fs_to_ds_valid = fs_valid && fs_ready_go && ~br_taken;

// br_bus = {br_taken(1), br_target(32)}，从 ID 直接反馈回 IF
assign {br_taken, br_target} = br_bus;
assign next_pc = (br_taken == 1) ? br_target : seq_pc;
注意这是一种"组合式 flush"：br_taken=1 的这一拍，IF 级的指令当场对 ID 不可见， ID 这一拍收不到东西（fs_to_ds_valid=0），下一拍 IF 已经按 br_target 取到新指令了。 代价是分支损失 1 个周期（取指级那一条作废）。
代价换来了什么：分支判断放在 ID 级，源操作数可以走前递，不需要像有些教材那样把分支挪到 EXE 级再算。

3.1 通用模型（最重要的一张图）

为什么要这样拆？
  • 时序分析只看"寄存器 → 寄存器"这一段组合路径。拆清楚了，哪一级是瓶颈一目了然。
  • 阻塞只影响寄存器（allowin 门控写入），组合逻辑永远在算，不会"卡住"。
  • 你要做时序优化时，就是在这两排寄存器之间做文章（比如本工程的乘法器就被挪出了前递逻辑锥）。

4 · 级间总线：位宽、打包与排线图

4.1 为什么要把几十个信号"打包"成一条 bus

每一级要传给下一级的信号少则几个、多则二十几个。如果逐个端口连线，顶层会变成一团乱麻， 而且漏连一个信号不会报错，只会静默出错。所以约定：

  • 打包成一条 xxx_bus，和一个 xxx_valid 一起往下传；
  • 打包侧和解包侧必须用同一个顺序（用 {} 拼接 / 拆分），顺序错了位就错位；
  • 指导书的经典好处：清空流水线时只要把 valid 清 0，不用把 data 清 0。

打包 / 解包顺序必须逐位对齐——这是本项目最阴险的一类 bug。
一旦 ID 侧改了顺序而 EXE 侧没改，综合不会报错、仿真前期也不一定报错， 只会在某条指令上算出莫名其妙的值。改总线时的铁律： 改一端必须立刻改另一端，并且数一遍总位数是否仍等于宏定义的位宽。

5 · 存储器：片选信号与 BRAM 实现

5.1 CPU 看到的 RAM 接口（6 个信号）

信号方向含义
xxx_sram_en出片选 / 访问使能：1 = 这一次访问有效。RAM 只在它为 1 时才动作
xxx_sram_we出字节写使能 4 位，每位对应一个字节。全 0 = 读
xxx_sram_addr出字节地址（32 位）
xxx_sram_wdata出写数据
xxx_sram_rdata入读数据（同步 RAM：下一拍才有效）

5.2 inst_sram_en：取指片选怎么来

// IF_stage.v
assign inst_sram_en    = to_fs_valid && fs_allowin;  // ★ 片选
assign inst_sram_we    = 4'h0;                       // 指令 RAM 永远只读
assign inst_sram_addr  = next_pc;
assign inst_sram_wdata = 32'b0;
assign fs_inst         = inst_sram_rdata;
为什么片选要 && fs_allowin？
fs_allowin=0 意味着 IF 级这一拍被堵住了，它手上的指令不能往下走。 如果这时还去读 RAM，那么这次读出来的指令在下一拍无处可去（IF 寄存器不允许更新）， 就等于白读一次、且把正确的下一次访问冲掉。所以片选必须和"我这一拍真的接收新 PC"严格同相。

5.3 data_sram_en：访存片选怎么来

// EXE_stage.v
assign data_sram_en    = es_valid && (es_res_from_mem || es_mem_we);  // ★ 片选
assign data_sram_we    = (es_valid && es_mem_we) ? es_store_we : 4'b0000;
assign data_sram_addr  = alu_result;      // 地址 = ALU 算出的 rj + imm
assign data_sram_wdata = es_store_wdata;

只有 load（es_res_from_mem）或 store（es_mem_we）才拉高片选。 普通算术指令不访问数据 RAM——这既是省电，也是避免误改内存。

字节写使能的译码（第 4 章内容，先认识一下）

wire [1:0] es_addr_low = alu_result[1:0];        // 字内字节偏移（小端）
wire [3:0] we_byte = 4'b0001 << es_addr_low;     // st.b：00→0001 01→0010 10→0100 11→1000
wire [3:0] we_half = es_addr_low[1] ? 4'b1100 : 4'b0011;  // st.h
wire [3:0] we_word = 4'b1111;                    // st.w

// 写数据"复制"到各字节通道，配合上面的 we 就能落到正确位置
wire [31:0] wdata_byte = {4{es_rkd_value[7:0]}};
wire [31:0] wdata_half = {2{es_rkd_value[15:0]}};

例如地址 ...01 写字节：we=0010，wdata = {d,d,d,d}， 只有 byte1 通道被打开 → 内存里只有 byte1 被改成 d，其余三个字节不受影响。

5.4 "片选齐备"的真正含义：bridge_1x2 的地址译码

CPU 只有一个数据口，但 SoC 里有两个从设备：数据 RAM 和 confreg（数码管/拨码开关等外设）。 片选在这里才体现出它的本质——按地址选出该响应的是哪一块：

// bridge_1x2.v
assign sel_conf = (cpu_data_addr & 32'h1fff_0000) == 32'h1faf_0000;  // 地址落在 0x1faf_xxxx
assign sel_sram = !sel_conf;

assign data_sram_en = cpu_data_en & sel_sram;   // ★ 给数据 RAM 的片选
assign conf_en      = cpu_data_en & sel_conf;   // ★ 给外设的片选
这里有一拍的时序陷阱：地址译码是组合的（当拍就知道选谁）， 但 RAM 的读数据下一拍才回来。所以要把"这一拍选的是谁"打一拍寄存器， 回来时才知道该采哪一路： 
always @(posedge clk) begin sel_sram_r <= sel_sram; sel_conf_r <= sel_conf; end
assign cpu_data_rdata = {32{sel_sram_r}} & data_sram_rdata
                      | {32{sel_conf_r}} & conf_rdata;

5.5 BRAM 是怎么实现的（两套，仿真和烧板不一样）

图 3 · 同一个 inst_ram，仿真与上板是两套完全不同的实现

仿真用的行为模型（你能在仿真里读懂的那一版）

module sync_ram #(ADDR_WIDTH=16, DATA_WIDTH=32, DEPTH=1<<ADDR_WIDTH) (...);
    reg [DATA_WIDTH-1:0] ram [0:DEPTH-1];

    // 按字节通道写
    for (i=0; i<NUM_BYTES; i=i+1)
        always @(posedge clk) if (we[i]) ram[address][i*8 +: 8] <= wdata[i*8 +: 8];

    // 同步读：en=1 时，在时钟沿把数据锁到 rdata（下一拍可见）
    always @(posedge clk) if (en) rdata <= ram[address];
endmodule

顶层怎么接（注意地址被截断了）

inst_ram inst_ram (
    .clka  (cpu_clk),
    .ena   (cpu_inst_en),        // ← inst_sram_en 直接当片选
    .wea   (cpu_inst_we),        // 4'h0，只读
    .addra (cpu_inst_addr[19:2]),// ★ 字节地址 → 字地址：去掉低 2 位
    .dina  (cpu_inst_wdata),
    .douta (cpu_inst_rdata)
);
为什么是 [19:2] 而不是 [21:2]？ 指导书里外接 BaseRAM 是 20 位地址所以用 [21:2]； 本工程用的是片内 BRAM，inst_ram 深度 256K 字 = 18 位地址，所以取 [19:2]（多留 1 位余量）。 这个细节说明：地址线宽度是由"实际挂了多大的存储器"决定的，不是固定的。

5.6 时序对齐：en、addr、rdata 差一拍

周期发生什么
NIF 送出 inst_sram_en=1、addr=next_pc；同一时钟沿上 BRAM 把 ram[addr] 锁进 douta；fs_pc 也更新为 next_pc；fs_valid 置 1
N+1fs_inst = inst_sram_rdata 已经是正确指令；fs_to_ds_bus = {inst, pc} 有效，fs_to_ds_valid=1；本拍结束时打入 ID 的 fs_to_ds_bus_r
N+2ID 级正式开始译码这条指令

这个"差一拍"是所有同步 BRAM 的共同特征。你可以在仿真波形里验证它： inst_sram_addr 变化后的下一个时钟沿，inst_sram_rdata 才跟着变。

6 · 第 2 章 · 数据前递与 Load-Use 阻塞

6.1 三种相关，我们只怕一种

类型全称例子五级流水要不要管
RAWRead After Write
（写后读，真相关）		add.w $r2,$r1,$r1
add.w $r3,$r2,$r2		要管（唯一真冲突）
WAWWrite After Write两条指令都写 $r2不管（顺序执行，后写的本来就在后面）
WARWrite After Read后条写 $r2，前条读 $r2不管（读在前，不会读错）

6.2 RAW 的四种"距离"

设指令 A 写 $r5，指令 B 读 $r5。B 在 A 后面第几条？这决定了怎么修：

距离A / B 所在级结果在哪怎么办
差 1 条A 在 EXE / B 在 IDEXE 的 ALU 输出（组合）从 EXE 前递（若 A 是 load 则见下）
差 2 条A 在 MEM / B 在 IDMEM 级寄存器里从 MEM 前递
差 3 条A 在 WB / B 在 IDWB 级寄存器里（还没写进堆）从 WB 前递（或寄存器堆内部直通）
差 4 条及以上A 已退出 / B 在 ID已经在寄存器堆里不用管，直接读堆

6.3 三条前递通路与优先级

图 4 · 前递多路选择器：EXE > MEM > WB > 寄存器堆
为什么优先级必须是 EXE > MEM > WB？
因为越靠前的级，指令越新。三条指令先后都写 $r5 时，正确的值一定是最晚那条（在 EXE 的那条）算出来的。 如果优先级反了，就会拿旧值覆盖新值——这是隐蔽且必然出错的。

6.4 真实代码

// ID_stage.v —— rj 的前递（rkd 完全同构，只是换 raddr2 / ds_use_rkd）
wire [31:0] rj_forward_data =
    (es_forward_valid && ds_use_rj  && (es_forward_dest == rf_raddr1)) ? es_forward_data :
    (mem_fwd_ok       && ds_use_rj  && (ms_forward_dest == rf_raddr1)) ? ms_forward_data :
    (ws_forward_valid && ds_use_rj  && (ws_forward_dest == rf_raddr1)) ? ws_forward_data :
                                                                         rf_rdata1;

// 前递源的有效条件（EXE 侧，见 EXE_stage.v）
assign es_forward_valid = es_valid && es_gr_we && (es_dest != 5'd0) && !es_mul_inst
                        && (!es_div_inst || es_div_ready);
assign es_forward_dest  = es_dest;
assign es_forward_data  = es_forward_result;   // ALU 或除法结果

三个条件缺一不可，逐个解释：

es_validEXE 级里确实有指令（否则气泡会伪装成前递源） es_gr_we这条指令真的会写通用寄存器（store / 分支不写） es_dest != 0目标不是 $r0（$r0 恒为 0，写了也丢弃） rf_raddr1 == dest我这条指令用的正是那个寄存器 ds_use_rj我这条指令真的把 rj 当源操作数用（见 §7 情况 3）

6.5 Load-Use：前递解决不了的那一种

看这条序列：

ld.w  $r5, 0($r1)      // A：从内存读
add.w $r6, $r5, $r7    // B：要用 $r5

A 到 EXE 级时，它手里还没有数据——它只算出了地址。真正的数据要等 A 走到 MEM 级、 从 data_ram 读回来才有。EXE 级前递递不出一个"还不存在的值"。

所以：load 的结果只能从 MEM / WB 前递。若消费者紧跟在 load 后面（差 1 条）， 必须阻塞 1 拍，把"差 1"变成"差 2"，再从 MEM 前递。 这就是 Load-Use 阻塞，也叫 load delay slot / pipeline interlock。 
// ID_stage.v
assign load_stall = es_is_load && (
    (ds_use_rj  && (rf_raddr1 != 5'd0) && (rf_raddr1 == es_forward_dest)) ||
    (ds_use_rkd && (rf_raddr2 != 5'd0) && (rf_raddr2 == es_forward_dest))
);

assign ds_ready_go = ~load_stall & ~div_stall & ~mul_stall & ~branch_load_stall;

阻塞时流水线发生什么（对照时序表看）

周期IFIDEXEMEMWB说明
1—add(B)ld(A)——es_is_load=1，dest=5，B 用 rj=5 → load_stall=1
2—add(B) 冻结气泡ld(A)—ID 不往下送，EXE 收到"空"；A 进入 MEM 读 RAM
3—add(B)add(B)气泡ld(A)B 终于进 EXE，同一拍从 MEM 前递拿到 $r5
注意第 2 拍：ID 冻结的同时，ds_allowin=0 → fs_allowin=0 → IF 也冻结， 整条流水线一起停一拍，而不是只有 ID 停。这正是 §2.4 讲的阻塞传播。

7 · 特殊情况全覆盖清单

下面每一条都是真实会出错或真实会浪费周期的情况。汇报时老师追问"你考虑了哪些边界"，照这个答。

情况 1 · 目标寄存器是 $r0（x0 恒零）

add.w $r0, $r1, $r2    // 写 $r0，约定上丢弃
add.w $r6, $r0, $r7    // $r0 必须读到 0

三处保护：前递源要求 dest != 5'd0；阻塞判断要求 rf_raddr != 5'd0； RegFiles 里 raddr==0 直接返回 32'h0。
漏掉会怎样：前递会把 add 的结果当成"新的 $r0 值"递出去，$r0 不再是 0，后续所有依赖零寄存器的指令全错。

情况 2 · 写者根本不写寄存器

分支、st.w、无条件跳转都不写通用寄存器。若只看 dest 相等就前递， 会把 store 的"地址"（alu_result）当成"结果"递给下一条指令。
保护：es_forward_valid 里有 es_gr_we。

情况 3 · 消费者这条指令根本不用那个源（最容易漏）

很多指令的 rk 字段不是寄存器号而是立即数的一部分。例如：

  • addi.w $rd, $rj, si12 —— rk 位实际是 i12[4:0]
  • slli.w $rd, $rj, ui5 —— rk 位就是移位量 ui5
  • jirl —— rk 位是 si16 的高位

这些时候 rf_raddr2 = rk 是一个立即数碰巧等于某个寄存器号。 若不加 ds_use_rkd 判断，会：

  • 误前递：rkd_value 被换成别的值（多数情况下因为 src2_is_imm 用不到它而无害，但很脏）；
  • 误阻塞：load_stall 无谓拉高 → 白白损失一个周期（性能问题，不是功能问题）。

本工程的写法：显式列出每条指令"到底用不用 rj / rkd"，得到 ds_use_rj 和 ds_use_rkd， 两个判断同时用于前递条件和阻塞条件。

情况 4 · store 的第二源是 rd 不是 rk

assign src_reg_is_rd = inst_beq | inst_bne | inst_st_all
                     | inst_blt | inst_bge | inst_bltu | inst_bgeu;
assign rf_raddr2 = src_reg_is_rd ? rd : rk;

LA32R 中 st.w $rd, $rj, si12 里要存的数据在 rd 位，地址基址在 rj。 所以 store / 条件分支的"第二源"要读 rd。
漏掉会怎样：ld.w $r5 紧跟 st.w $r5, ... 时，load_stall 判的是 rk 位， 发现不相等 → 不阻塞 → 把旧值写进内存，这是真错误。

情况 5 · load → load（地址相关）

ld.w $r5, 0($r1)
ld.w $r6, 0($r5)     // 地址依赖 $r5

第二条 load 的 ds_use_rj = 1（inst_ld_all 在列表里），rf_raddr1 = 5 → 阻塞 1 拍 ✅。

情况 6 · load → 分支（控制 + 数据双重相关）

ld.w  $r5, 0($r1)
beq   $r5, $r6, label   // 要拿 $r5 比较

inst_beq 在 ds_use_rj 和 ds_use_rkd 列表里，两个源都能触发 load_stall ✅。
第 5 章补充本工程额外加了 branch_load_stall，让分支再多等一拍走 WB 前递—— 这是为了切断时序长路径（data_ram → 分支比较 → IF → inst_ram），不是功能必需。

情况 7 · 同一寄存器被连续写三次（优先级检验）

add.w $r5, $r1, $r2    // 此时已在 WB
add.w $r5, $r3, $r4    // 此时已在 MEM
add.w $r5, $r6, $r7    // 此时在 EXE（最新）
sub.w $r8, $r5, $r9    // ID：必须拿 EXE 那条的结果

四级 MUX 从上往下判，第一条命中就返回 → 取到 EXE 的值 ✅。优先级反了就会取到 WB 的旧值。

情况 8 · 乘法 / 除法结果不参与 EXE 前递 第 5 章

乘法器延迟大，除法要多拍。它们的处理方式和 Load-Use 完全同构，只是换了触发条件：

assign div_stall = es_is_div && !es_div_ready && ( ...源寄存器命中... );
assign mul_stall = es_is_mul               && ( ...源寄存器命中... );

第 1、2 章先记住一句："谁的 EXE 级结果不可用时，就把消费者堵在 ID 一拍"， 后面章节只是往 load_stall 旁边再加几个同构的 xxx_stall。

情况 9 · "第四条前递通路"——寄存器堆内部直通

// RegFiles.v
assign rdata1 = (raddr1 == 5'b0)            ? 32'h0 :
                (wen && (raddr1 == waddr))  ? wdata : rf[raddr1];

WB 级这一拍正在写 $r5，ID 这一拍正好读 $r5： rf[5] 还是旧值（要到本拍时钟沿才更新），所以这里直接把正在写的 wdata 送出去。 它和外部 ws_forward 做的是同一件事——冗余但零成本，属于双保险。

情况 10 · 复位后的"气泡"

复位时五级全部 valid=0。第 1 拍只有 IF 拿到 to_fs_valid=1， 要等 5 拍 第一条指令才到 WB。这 5 拍里各级的 valid 都是 0， 下游不会把气泡当成有效指令执行——这就是 valid 位的价值。

7.1 汇报时的三句话提纲

  1. 骨架：五级流水 IF/ID/EXE/MEM/WB，每级之间用"数据总线 + valid 位"构成的流水线缓存隔断， 级间用 valid / ready_go / allowin 三信号握手，阻塞沿 allowin 逐级向前传播。
  2. 存储：指令 RAM 与数据 RAM 都做成同步 BRAM，en 作片选、we[3:0] 作字节写使能， 地址取 [19:2] 转成字地址；数据口经 bridge_1x2 按地址译码在 data_ram 与 confreg 之间片选。
  3. 冲突：只处理 RAW。三级前递 EXE>MEM>WB（越新越优先）， load 结果最早只能从 MEM 前递，因此"load 后紧跟消费者"必须用 load_stall 阻塞一拍； 所有阻塞、前递判断都要排除 $r0、排除不写寄存器的指令、排除不用该源的指令。

7.2 老师可能追问 & 标准答案

问题怎么答
流水线为什么能加速？不是单条变快，是吞吐率提升：理想 CPI → 1。单条指令的延迟反而略增（多了级间寄存器）。
为什么必须有级间寄存器？否则新值会组合地穿透到后级，把上一条指令的中间结果冲掉。
ready_go 和 allowin 区别？ready_go 是本级自己干完没（内部原因）；allowin 是后级收不收（外部原因）。两个都满足才能前进。
为什么 WB 的 allowin 没有后级项？它是最后一级，下游是寄存器堆，永远可写，不会反压。
前递优先级为什么 EXE 最高？越靠前的级指令越新，同一寄存器多次写入时应取最新的那次。
load 为什么必须阻塞一拍？load 在 EXE 级只有地址没有数据，数据要等 MEM 级读 RAM 才有，前递递不出不存在的值。
分支怎么处理的？分支在 ID 级判断，br_taken=1 时组合地把 fs_to_ds_valid 拉低，取消已预取的那条；代价 1 个周期，LA32R 无延迟槽。
代价与不足？分支固定损失 1 拍；Load-Use 损失 1 拍；未做 Cache / 分支预测 / 乱序（可列为后续工作）。
