0 · 学前预备：这一章为什么和前面不一样

前两份讲义（第 1–2 章、第 3–4 章）讲的是"在已有骨架上填指令"—— 13 条算逻、4 条转移、6 条访存，alu.v 一行都没改，全部靠复用。 这一章不一样：第一次真正往 CPU 里加运算部件。

实验一（第 1–2 章）
搭骨架：五级划分、握手规范、级间总线、前递与阻塞。
关键词：结构
实验二（第 3–4 章）
填指令：9 条算逻 + 4 条转移 + 6 条访存，零新增部件。
关键词：复用
实验三上（第 5 章·本册）
加部件：1 个 DSP48 乘法器 + 2 个 32 拍除法器。
关键词：时序与多拍
本课最核心的一句话（请背下来，汇报时第一句就说它）
第 5 章真正难的地方不是算术——LA32R 只要求 32 位整数乘除，Verilog 一行 * 就能出乘法， 除法也是一个教科书算法。难的是把这两个部件塞进五级流水线而不破坏它：
  • 乘法器太快、太大——它是组合逻辑，一旦被并进 alu_result 的锥里， 就会顺着前递链路串到"分支比较 → 取指地址"，形成跨三级的长路径，50 MHz 直接不收敛；
  • 除法器太慢——一次除法要 32 个时钟，而流水线默认每一级都是 1 拍， 必须给它加"允许占住本级多拍"的握手通道。
这两个问题一个关于空间（放在哪），一个关于时间（等多久），构成本章的全部难点。

1 · 七条乘除指令：编码、语义、三个"对偶"

1.1 编码：和移位指令同一个"大家族"

这 7 条都是 3R 格式（rd, rj, rk，无立即数）：op[31:26]=0x00、 op[25:22]=0x0。它们内部靠 op[21:20] 分成两族，再用 op[19:15] 区分具体指令：

指令[31:26][25:22][21:20][19:15]语义
mul.w0x000x00x10x18rd ← (rj × rk)[31:0]
mulh.w0x000x00x10x19rd ← 有符号乘积[63:32]
mulh.wu0x000x00x10x1ard ← 无符号乘积[63:32]
div.w0x000x00x20x00rd ← 有符号商
mod.w0x000x00x20x01rd ← 有符号余数
div.wu0x000x00x20x02rd ← 无符号商
mod.wu0x000x00x20x03rd ← 无符号余数
sll.w（第3章）0x000x00x10x0e对照：移位与乘法同在 [21:20]=0x1 族

真实译码取自 ID_stage.v，四个字段全部写满：

// ---- 第 5 章：乘除指令（均为 3R 格式，op[31:26]=000000、op[25:22]=0000）----
//   op[21:20]=01 → 乘法类：11000=mul.w  11001=mulh.w  11010=mulh.wu
//   op[21:20]=10 → 除法类：00000=div.w  00001=mod.w  00010=div.wu  00011=mod.wu
assign inst_mul_w   = op_31_26_d[6'h00] & op_25_22_d[4'h0] & op_21_20_d[2'h1] & op_19_15_d[5'h18];
assign inst_mulh_w  = op_31_26_d[6'h00] & op_25_22_d[4'h0] & op_21_20_d[2'h1] & op_19_15_d[5'h19];
assign inst_mulh_wu = op_31_26_d[6'h00] & op_25_22_d[4'h0] & op_21_20_d[2'h1] & op_19_15_d[5'h1a];
assign inst_div_w   = op_31_26_d[6'h00] & op_25_22_d[4'h0] & op_21_20_d[2'h2] & op_19_15_d[5'h00];
assign inst_mod_w   = op_31_26_d[6'h00] & op_25_22_d[4'h0] & op_21_20_d[2'h2] & op_19_15_d[5'h01];
assign inst_div_wu  = op_31_26_d[6'h00] & op_25_22_d[4'h0] & op_21_20_d[2'h2] & op_19_15_d[5'h02];
assign inst_mod_wu  = op_31_26_d[6'h00] & op_25_22_d[4'h0] & op_21_20_d[2'h2] & op_19_15_d[5'h03];
★ 坑 1：乘法和移位是"同族兄弟"，译码必须写满四个字段。
sll.w / srl.w / sra.w 的编码是 [21:20]=0x1 + [19:15]=0x0e/0x0f/0x10， 和 mul.w 的 [21:20]=0x1 + [19:15]=0x18 只差最后一个字段。 如果偷懒少写 op_21_20_d（觉得"反正 [19:15] 不一样"）， 短期看不出问题，但只要以后再加一条 [19:15]=0x18 的其它族指令就会静默撞车。 规则：3R 指令的译码前缀一律写满 op_31_26 / op_25_22 / op_21_20 三段，再用 op_19_15 分流。

1.2 三个"对偶"：把这 7 条压成 3 组来理解

七条指令看着多，其实只有三个维度上的"对偶"，每个维度只要一个控制位：

对偶控制位区别实现代价
低半 / 高半alu_op[12] / [13] / [14] mul.w 取乘积 [31:0]；mulh.w / mulh.wu 取 [63:32] 一个 3 选 1 MUX
有符号 / 无符号（乘）alu_op[13] vs [14] 同一个 64 位乘积，一个来自 $signed 乘法，一个来自普通乘法 两个 * 表达式（共用 DSP48）
商 / 余数ds_div_rem 除法器同时输出商和余数（64 位：[63:32]=商，[31:0]=余数），div 取高半、mod 取低半 一个 2 选 1 MUX（不用算两遍）
有符号 / 无符号（除）ds_div_signed 决定用哪一个除法器实例 两份除法器 + 一个 MUX
这是一个可以直接讲的"省硬件"点：div.w 和 mod.w 在硬件上共用同一次除法。 除法器一拍一拍算出来的商和余数是同时产生的（商逐位从低位补进 quo_r， 余数就留在 rem_r 里），所以不存在"算两遍"的问题。 把它们做成两条独立指令，只是为了让指令集写起来方便。

1.3 为什么 mul.w 与符号无关，而 mulh 必须区分

这是补码乘法最漂亮的一个性质：乘积的低 32 位与"是否符号扩展"完全无关， 只有高 32 位不同。用工程里真实跑过的一组向量算一下就很清楚：

操作数乘积 [63:32]乘积 [31:0]结论
a = 0x99a451b0
b = 0xbe3d9998
（按有符号乘）		 0x1a4b01ae0x8552b080 低半完全相同（0x8552b080）
高半完全不同
→ mul.w 不需要知道符号
→ mulh.w / mulh.wu 必须分成两个表达式
同一对操作数
（按无符号乘）		 0x722cecf60x8552b080

工程里的实现就是照这个性质写的——算两个乘积，但只按需取半边：

wire signed [63:0] mul_signed_prod   = $signed(es_alu_src1) * $signed(es_alu_src2);
wire        [63:0] mul_unsigned_prod = es_alu_src1 * es_alu_src2;

wire [31:0] mul_result = alu_op[12] ? mul_unsigned_prod[31:0]  :  // mul.w  ：低半，符号无关
                          alu_op[13] ? mul_signed_prod  [63:32] :  // mulh.w ：有符号高半
                                       mul_unsigned_prod[63:32];   // mulh.wu：无符号高半
为什么 mul.w 用的是 mul_unsigned_prod[31:0] 却没错？
因为低 32 位是"模 232"意义下的结果，而 ×232 的倍数对它没有影响—— 符号扩展只是在被乘数高位补 1，等价于多加了若干个 232 的倍数。 这也是为什么 mul.w 不会溢出、也不会报错，它天生就是"截断"语义。

用真实测试向量对照一下（n32_mul_w.S 与 n33_mulh_w.S 的第 1 行操作数完全一样）：

// n32_mul_w.S   —— 取低半
TEST_MUL_W   (0x45b90738, 0xd70d64f0, 0x0a20a480)

// n33_mulh_w.S  —— 同一对操作数，取有符号高半
TEST_MULH_W  (0x45b90738, 0xd70d64f0, 0xf4d903bb)

1.4 除法语义：商向零取整，余数与被除数同号

LA32R（以及 C 语言）规定的是"截断除法"，不是数学上的 floor 除法：

  • 商向零取整：−7 / 2 = −3（不是 −4）
  • 余数符号跟随被除数：−7 % 2 = −1，7 % −2 = 1
  • 永远满足 被除数 = 除数 × 商 + 余数

工程里真实通过的 4 组向量，div.w（n30）与 mod.w（n35）操作数一一对应，正好把这三条性质演示完：

被除数除数div.w 商mod.w 余数解读
0x56bedfa40x208314000x000000020x15b8b7a4 两正数：545461248×2 + 364427172 = 1455349668 ✓
0x53eb4a700x07e13dd10x0000000a0x051ee046 普通情况：商 10、余 85909574
0x323676e00xdc3a3f100xffffffff0x0e70b5f0 异号：842430176 ÷ (−600162544) = −1.4 → 商 −1（向零）； 余数 = +242267632，与被除数同号
0xfda5ea8a0xfac1873c0x000000000xfda5ea8a 同负且 |a|<|b|：商 0，余数 = 被除数本身（负数）
★ 坑 2：如果你自己写除法器，最容易错的就是"负数"。
很多人的第一版会把 −7 / 2 算成 −4（floor），因为恢复余数法在绝对值域上算完以后， 商的符号是单独决定的——你必须在最后一步补上"向零取整"的修正，否则差 1。 本工程的做法是：全部转到绝对值域算，最后再按符号取反（见 §3.4）， 这样天然得到截断语义，不需要额外修正。

2 · 乘法器：一行 * 就够，但必须放在对的地方

2.1 算法上零难度，工程上是本章最大的坑

指导书说"可以直接使用 Verilog 的乘号实现"，本工程就是这么做的—— Vivado 会把 32×32 的 * 映射到 Artix-7 的 DSP48E1 硬核上， 几乎不消耗 LUT，单周期出结果。所以乘法在"功能"层面是完全不用操心的。

但如果你顺手把它并进 alu.v 的那棵"与-或树"里（毕竟独热码 12/13/14 三个位都留好了）， 综合能过、仿真能过、RTL 逻辑也全对，唯独上板一定错。这是本章最值得讲的故事。

2.2 ★ 时序灾难：乘法器为什么不能进 alu_result

图 5A · 同一个乘法器，放在 alu_result 锥里 vs 放在独立结果通路上：功能完全一样，时序差了一个数量级

这条长路径是怎么形成的？把五级串起来看就明白了：

  1. alu_result 不只是"送下一级"的结果，它同时是 EXE→ID 前递的数据源 （es_forward_data）；
  2. ID 级用前递后的值做分支比较（rj_eq_rd 等）；
  3. 分支结果 br_taken 直接驱动 br_bus，决定 IF 级的下一拍 PC。

于是"乘法器 → 或树 → 前递 MUX → 比较器 → 下一 PC"在一个时钟周期内串成一条组合链。 这已经不只是跨越三级流水，而是把三条完全不同的功能路径焊在了一起。

★ 坑 3（本项目最贵的一个坑，修了四轮）：
第一轮修复的直觉是"给乘法结果加一个 MUX，让它别进前递"——无效。 因为综合器做静态时序分析时看的是逻辑锥而不是"最终会不会被选中"： 只要乘法器的输出还挂在 alu_result 这条网上， 它就是这个网的逻辑锥的一部分，路径照旧存在。

正确做法：物理上换数据源——乘法结果根本不参与 alu_result 的计算， 而是走一条独立的结果通路，终点是触发器： 
// es_forward_result：可能参与 EXE→ID 前递的结果（ALU / 除法），逻辑锥里没有乘法器
wire [31:0] es_forward_result = es_div_inst ? div_result : alu_result;
// es_final_result  ：送 MEM / 写回的最终结果（乘法 > 除法 > ALU），乘法只出现在这里
wire [31:0] es_alu_mul_result = es_mul_inst ? mul_result : es_forward_result;

2.3 附带代价：乘法结果不能走 EXE 前递，只好加一个 mul_stall

把乘法器搬走之后，一个新的问题出现了：乘法结果不再出现在 EXE 级的前递口上。 那么紧跟在乘法后面的指令要用它的结果怎么办？

答案是多等一拍——下一拍乘法已经进入 MEM 级，它的结果躺在 es_to_ms_bus_r 这个触发器里，由 MEM 级前递提供，路径极短。

// 乘法结果阻塞（第 5 章·时序修复）：乘法器组合延迟过大，其结果不参与 EXE 级前递。
// 当 EXE 级是一条乘法指令、且本指令的正源寄存器正好是它的目标寄存器时，阻塞 ID 一拍。
assign mul_stall = es_is_mul && (
    (ds_use_rj  && (rf_raddr1 != 5'd0) && (rf_raddr1 == es_forward_dest)) ||
    (ds_use_rkd && (rf_raddr2 != 5'd0) && (rf_raddr2 == es_forward_dest))
);
这段代码和 load_stall 是同一个模子刻出来的—— 都是"后级结果还没到寄存器里，前级先停一拍"。区别只是： load 慢是因为存储器是同步读，mul 慢是因为组合路径太长。 把它们写成同一个模式，既好懂也好维护。

2.4 一个顺带的性能知识点

mul_stall 只在"紧邻的指令要用乘法结果"时生效，代价是 1 个气泡。 如果你把编译出来的代码里 mul.w 后面隔一条无关指令，就完全没有停顿。 汇报时可以主动提这个："处理器微架构的一个小改动，编译器排一下指令顺序就能把损失吃掉"—— 这是很好的"体系结构—编译器协同"话题。

3 · 除法器：32 拍迭代的恢复余数法

3.1 为什么除法不能像乘法那样"一行搞定"

乘法是"一层层的部分积相加"，32×32 只有 32 个部分积，DSP48 硬核内部就把它们压完了。 除法不行——它本质上是串行的试商：每一位商都要看"当前余数够不够减"， 而这个判断依赖上一位的结果。这是一个真正的迭代过程，没有已知的常数级组合实现。

方案延迟资源评价
组合除法器（一次算完）约 32 级减法/比较串联极大延迟轻松超过 20 ns，直接不可用
迭代除法（本工程）32 拍一个 33 位减法器 + 若干移位寄存器资源极少、时序轻松，代价是延迟
SRT / 基-4 除法约 16 拍甚至更少需要商选择表，控制复杂性能好但课设收益不高
一句话总结：除法用时间换面积。在 50 MHz、BRAM 已经占了器件 87% 的前提下， 把除法做成 32 拍迭代是唯一现实的选择——它只多占一个 33 位减法器，几乎不增加布线压力。

3.2 恢复余数法：一拍到底在算什么

图 5B · 恢复余数法：32 拍迭代，一拍一个减法，商从右往左长出来

用一个小例子把 32 拍"压缩"成 4 拍看清楚（13 ÷ 3，用 4 位演示）：

拍rem_shift = {rem, 被除数下一位}≥ 3 ?rem_nextquo_next
1{0000, 1} = 1否10000
2{0001, 1} = 3是 → 3−300001
3{0000, 0} = 0否00010
4{0000, 1} = 1否10100
结果商 0100 = 4，余 1 → 13 = 3×4 + 1 ✓

注意被除数是从高位往低位一位一位喂进去的（所以每拍要 dividend_r = {dividend_r[30:0], 1'b0} 左移）， 商是从低位往高位长出来的（quo_r = {quo_r[30:0], rem_ge}）。一进一出方向相反，这是最容易写反的地方。

3.3 divider.v 的内部结构

reg [31:0] dividend_r;   // 被除数绝对值，逐拍左移，最高位被"喂"进余数
reg [31:0] divisor_r;    // 除数绝对值（不变）
reg [32:0] rem_r;        // 余数，多 1 位用来容纳移位后的进位
reg [31:0] quo_r;        // 商（绝对值），逐拍从低位补入
reg [ 5:0] cnt;          // 剩余迭代次数，32 → 1
reg        quo_sign;     // 商符号 = 被除数符号 ^ 除数符号
reg        rem_sign;     // 余数符号 = 被除数符号

// 一拍迭代的全部组合逻辑（就这么四行）
wire [32:0] rem_shift = {rem_r[31:0], dividend_r[31]};
wire        rem_ge    = (rem_shift >= {1'b0, divisor_r});
wire [32:0] rem_next  = rem_ge ? (rem_shift - {1'b0, divisor_r}) : rem_shift;
wire [31:0] quo_next  = {quo_r[30:0], rem_ge};
为什么余数要 33 位？因为 rem_shift 是把 32 位余数左移一位再拼 1 位，一共 33 位。 如果只用 32 位，最高位会在移位时丢掉——而"丢掉的最高位"恰恰可能让 rem_shift 超过一个 32 位数，导致比较结果出错。这是手写除法器第二容易错的地方（第一是符号）。

3.4 符号处理：绝对值域相除 + 末拍取反

本工程的做法是把有符号除法完全化成无符号除法：

// ① 进入时取绝对值
wire [31:0] dividend_abs = (SIGNED && s_axis_dividend_tdata[31]) ? (~s_axis_dividend_tdata + 32'b1)
                                                             :   s_axis_dividend_tdata;
wire [31:0] divisor_abs  = (SIGNED && s_axis_divisor_tdata[31])  ? (~s_axis_divisor_tdata  + 32'b1)
                                                             :   s_axis_divisor_tdata;

// ② 32 拍无符号迭代（同上）

// ③ 末拍按符号还原：求相反数 = 取反加一
wire [31:0] quo_final = quo_sign ? (~quo_next       + 32'b1) : quo_next;
wire [31:0] rem_final = rem_sign ? (~rem_next[31:0] + 32'b1) : rem_next[31:0];
为什么这样能自动得到"向零取整"？
因为绝对值域上的除法本身就是截断的：|a| / |b| 是无符号整数除，天然向下取整 （在非负数域上"向下"就是"向零"）。然后再给商单独加符号—— 于是 −7 / 2 走的是 7/2 = 3，再加负号得 −3，正是不补 1 的截断结果。
如果反过来在补码域直接迭代（不取绝对值），负数会得到 floor 语义 −4，与 LA32R 不符。

余数为什么"跟着被除数"？看这两行的 rem_sign 就懂了：

quo_sign <= SIGNED ? (s_axis_dividend_tdata[31] ^ s_axis_divisor_tdata[31]) : 1'b0;
rem_sign <= SIGNED ?  s_axis_dividend_tdata[31]                              : 1'b0;

商看两者的符号异或，余数只看被除数的符号——这就是 §1.4 那张表第 3、4 行的来历。

3.5 EXE 级怎么"等"这 32 拍：握手 + 锁存

图 5C · 除法指令的握手时序：靠 es_ready_go 让本级"占住" 34 拍（图中省略中间的 30 拍迭代），后级不冻结、前级自动停

关键只有两句话：

// 普通指令 ready_go 恒为 1；除法指令要等结果就绪
assign es_ready_go    = !es_div_inst || es_div_ready;
assign es_allowin     = !es_valid || (es_ready_go && ms_allowin);
assign es_to_ms_valid = es_valid && es_ready_go;
这就是当初设计 ready_go / allowin 握手规范的价值。
如果每一级都硬编码成"一拍一级"，加一个多拍部件就得大改。 而因为本工程从一开始就用"本级是否准备好往下走"这个抽象， 第 5 章加除法时只改了一行 es_ready_go：
  • ms_allowin 不变 → MEM 级完全不知道前面卡住了；
  • ID 级也不变 → 它只会发现 es_allowin=0，于是自己停下、把 ds_valid 保持住。
汇报时这是一个极好的"设计抽象带来的可扩展性"案例。

三个必须处理的状态细节

寄存器作用不写会怎样
div_sent记录"这次除法请求已经握手成功" 除法器空闲后 tready 重新拉高，而 tvalid 还高高挂着 → 除法器以为又来了一次新除法，重新算 32 拍，永远出不来
div_done记录"结果已经锁存" m_axis_dout_tvalid 只持续 1 拍。如果这一拍 ms_allowin=0（MEM 级反压），结果就凭空消失了
div_result_r锁存住那个 32 位结果 同上，配合 div_done 使用
 
else if (es_div_inst && es_ready_go && ms_allowin) begin
    // 除法指令本拍流出 EXE，控制状态复位，准备迎接下一条除法指令
    div_sent <= 1'b0;
    div_done <= 1'b0;
end
else begin
    if (div_handshake) div_sent <= 1'b1;              // 已握手 → 下一拍撤销 tvalid
    if (div_dout_valid) begin                          // 结果有效 → 立刻锁存
        div_done     <= 1'b1;
        div_result_r <= div_result_now;
    end
end

3.6 为什么要例化两个除法器

SIGNED 是 divider 的参数（不是在运行期判断的）， 因为"要不要取绝对值"会改变整个数据通路的接线：

// 有符号除法器（div.w / mod.w）
divider #(.SIGNED(1)) u_divider_signed (
    .s_axis_dividend_tvalid (div_req &  es_div_signed),
    .s_axis_dividend_tdata  (es_alu_src1),          // 被除数 = rj
    .s_axis_divisor_tdata   (es_alu_src2),          // 除数   = rk
    ...
);
// 无符号除法器（div.wu / mod.wu）
divider #(.SIGNED(0)) u_divider_unsigned (
    .s_axis_dividend_tvalid (div_req & ~es_div_signed),
    ...
);

两个实例共享同一个 div_req，但 tvalid 上各与一个使能项相与， 所以每次只有真正需要的那一个被激活。综合时 Vivado 会做资源共享之外的死逻辑消除， 不会真的布两套完整电路那么可怕——但它确实占两份 33 位减法器。

★ 坑 4：别在 testbench 里"连续两条除法背靠背"却不检查中间隔了几拍。
由于 div_sent 在指令流出那一拍才清零，两条紧邻的除法指令之间 至少会有一个气泡（EXE 必须先回到 IDLE 才能接收下一次握手）。 这不是 bug，是 AXI-Stream 式握手 + 非流水除法器的必然结果。 如果要做"每拍都能起一次除法"的除法器，就得做流水化除法器（32 级流水）， 那是另一种设计权衡，本课设不需要。

3.7 除零怎么办

LA32R 规定：除数为 0 时结果不可预测，但不产生任何异常。
本工程的实现（见 divider.v 文件头注释）： 由于 divisor_abs = 0，rem_ge = (rem_shift >= 0) 恒为真， 所以商逐位全补 1 → 商 = 0xFFFFFFFF；余数不减任何东西，逐拍左移吸收被除数 → 余数 = 被除数。
这个结果是"确定的任意值"，符合手册要求，也让仿真可复现 （否则 X 传播会把整条流水线带崩）。
注意：本工程的 func 测试里没有除数为 0 的用例（只有被除数为 0 的）， 所以这条行为没被验证过——但它是"良定义"的，不影响判分。

4.2 除法为什么不阻塞后级？

一个常见误解是"除法慢，所以整条流水线都停下来"。实际不会： es_ready_go=0 只让本级不走，MEM/WB 继续把前面已进来的指令排空， ID 级则自动停住不再送新指令。效果等价于插入气泡，而不是全局暂停。

唯一的代价是性能：一条 div.w 占 34 拍，等于浪费了 33 个流水级槽位。 如果代码里有一段密集除法（比如软件除法算法），性能会明显下降。 汇报时可以提一句"这就是为什么现代处理器要么做流水化除法器，要么干脆不提供除法指令" （RISC-V 的 M 扩展就把除法留成可选的、多拍的）。

4.3 第 5 章给级间总线加了几个字段？

答案有点反直觉：只往 ID→EXE 加了 3 位（div_en / div_signed / div_rem）。 EXE→MEM、MEM→WB 一位都没加——因为一旦出了 EXE，乘法和除法的结果 跟一条 add.w 的结果没有任何区别，都是 ms_alu_result。

这是一个很好的"信息最小化"设计点：控制信息只在需要它的那一级存在。 乘法/除法的"身份"在 EXE 级就用完了（选哪半边结果、用哪个除法器）， 没有理由再往后面传。总线越窄，布线越松，时序越好。

5.2 测试宏长什么样

#define TEST_DIV_W(in_a, in_b, ref) \
    li.w t0, in_a; \
    li.w t1, in_b; \
    div.w t3, t0, t1; \
    li.w t4, ref; \
    bne t4, t3, inst_error

所以 inst/n30_div_w.S 里每一行就是一整段"装数 → 执行 → 比对"：

TEST_DIV_W(0x56bedfa4, 0x20831400, 0x00000002)   // 我们的 CPU 必须算出 0x00000002
TEST_DIV_W(0x323676e0, 0xdc3a3f10, 0xffffffff)   // 异号大数：结果必须是 -1
TEST_DIV_W(0xfda5ea8a, 0xfac1873c, 0x00000000)   // 同负且 |a|<|b|：商 0
★ 为什么这几组向量特别值得关注？
因为它们是专门用来打"朴素实现"的：
  • 如果除法器没做符号处理 → 异号那组直接错。
  • 如果把除法实现成 floor（向下取整）→ 0x323676e0 / 0xdc3a3f10 会算出 −2， 而正确答案是 −1，差 1。
  • 如果余数符号跟着除数走（几何除法的直觉）→ n35 那组 0x0e70b5f0 会算成负数。
  • 如果 mulh.w 与 mulh.wu 共用一个表达式 → n33 / n34 至少一个全错。
这四条正好对本章的四个设计决策，一处写错就是一个测试点红掉——所以 func 的判分很"讲理"。

5.3 测试机制：ref 是怎么来的

和前面几章一样，ref（参考值）是由另一套独立实现的 LoongArch 语义在编译前算好、 作为立即数编进程序的（li.w t4, ref）。CPU 算出的结果与它不等就跳 inst_error。 这等于用一个"外部阅卷老师"给我们的 CPU 判卷，比自己写波形断言可靠得多。

仿真侧还有第二重保险：把每条指令的写回结果逐拍与官方 golden_trace.txt 比对，任何一条对不上就立刻报错并停在当前 PC。

8 · 汇报要点与老师常问的 8 个问题

8.1 三分钟汇报骨架

  1. 先定位：第 5 章是第一次"加硬件"——1 个 DSP48 乘法器 + 2 个 32 拍除法器； 难点不在算术，在时序和多拍握手。
  2. 乘法：* 一行出结果，映射到 DSP48；关键是结果必须走独立通路， 不能并进 alu_result，否则乘法器被吸进前递逻辑锥，跨三级长路径 21~22 ns。
  3. 除法：32 拍恢复余数法，绝对值域迭代 + 末拍按符号还原，天然得到"向零取整"； div/mod 共用一次除法取不同半边；靠 es_ready_go 占住 EXE 34 拍。
  4. 代价：mul_stall 1 拍、div_stall 最多 34 拍； 五个 *_stall 用同一个模板，可维护。
  5. 验证：EXP7 = 46 个测试点（第 5 章贡献 7 个、1060 组向量）全过； WNS +0.782 ns、0 违例。

8.2 老师常问的 8 个问题

Q1：乘法器为什么直接用 *，不自己写部分积？
因为 Vivado 会把 32×32 的 * 直接映射到 Artix-7 的 DSP48E1 硬核： 几乎不耗 LUT、单周期出结果。自己写部分积（比如基-4 Booth + Wallace 树）反而会 铺满 LUT，挤占本来就很紧张的布线资源（本设计 BRAM 已占 87.67%）。 有硬核就用硬核，这是 FPGA 设计的常识。
Q2：为什么必须把乘法器搬出 alu.v？只改 MUX 行不行？
不行。静态时序分析看的是逻辑锥，不是"运行时会不会被选中"。 只要乘法器的输出还挂在 alu_result 这条网上，它就是这个网的锥内逻辑， 综合器剪不掉（因为 op_mul 是运行期信号、不是可优化的常量）。 必须在物理上换数据源：让乘法结果根本不参与 alu_result 的计算， 而是直接进 es_final_result → EXE→MEM 寄存器。
Q3：那乘法结果还能前递吗？会不会影响性能？
不能从 EXE 级前递了（因为 es_forward_data 里刻意不含乘法器）。 改用 MEM 级前递——下一拍乘法已进入 MEM，它的结果躺在 es_to_ms_bus_r 触发器里，路径极短。 代价是紧邻的依赖指令多停 1 拍（mul_stall）。 1 拍的代价换来时序收敛，完全值得；而且编译器只要在乘法后面排一条无关指令就能吃掉这 1 拍。
Q4：除法为什么不单周期做完？
除法本质是串行试商：每一位商都要判断"当前余数够不够减"，而这个判断依赖上一位的结果， 没有常数级的组合实现。组合除法器需要约 32 级减法/比较串联，延迟远超 20 ns。 所以用时间换面积：32 拍迭代，只占一个 33 位减法器，时序轻松。
Q5：为什么选"恢复余数法"，不用"加减交替法"（不恢复余数）？
加减交替法每拍少一次"恢复"，但代价是每拍都要做一次加或减（由上一拍余数的符号决定）， 控制更绕，且最后可能要多一次"修正"步骤。
恢复余数法的"恢复"在本工程里根本不需要真的加回去——直接用 MUX 选回原值 （rem_next = rem_ge ? rem_shift - divisor : rem_shift）， 代价只是一个 33 位 2 选 1，比一次加法便宜得多。所以这里恢复余数法反而更简单。
Q6：有符号除法怎么处理？"向零取整"怎么保证？
分三步：① 进入时把被除数和除数都取绝对值；② 在绝对值域做 32 拍无符号迭代； ③ 末拍按符号还原（取反加一）。
关键在于：绝对值域的无符号整数除法本身就是截断的（非负数上"向下"等于"向零"）， 所以 −7 / 2 走的是 7/2 = 3，加负号得 −3，正是 LA32R 要的结果。 如果反过来在补码域直接迭代，会得到 floor 语义 −4，与手册不符。
Q7：div.w 和 mod.w 要算两遍吗？为什么要例化两个除法器？
不用算两遍。恢复余数法在迭代过程中，商（quo_r）和余数（rem_r） 是同时产生的——商逐位从低位补进去，余数就留在寄存器里。 除法器输出 64 位：[63:32]=商、[31:0]=余数， div 取高半、mod 取低半，只差一个 MUX。
例化两个除法器不是为了 div/mod，而是为了有符号/无符号： SIGNED 是编译期参数（决定要不要插取绝对值和符号还原的逻辑）， 不能在运行期切换，所以只能各做一份。
Q8：除数为 0 怎么办？为什么不触发异常？
LA32R 规定除 0 不产生异常，结果不可预测。本工程给出一个确定但任意的结果： 除数绝对值 0 → rem_ge 恒真 → 商逐位全 1 = 0xFFFFFFFF，余数不减 → 余数 = 被除数。
这样做的工程意义是不让 X 传播：如果返回 32'bx，一旦被写进寄存器再参与运算， 整条流水线都会变成 X，仿真时根本定位不到问题。"确定的错值"比"不可控的 X"好得多。
